# トレイと通知

- 対象: 段階1
- 最終更新: 2026-10-08
- 前提: Codexのジョブは、**同じワークスペースでも別のワークスペースでも、複数が同時に動く**。表示はどれも、同時に何件動いていても見分けられるようにする。
- 前提として読む文書: [監視コア](monitor-core.md)（実効状態と変更イベント）、[アプリの土台](app-shell.md)

ウィンドウを開いていなくても状況がわかるようにする部分。Tauri本体（`src-tauri/src/`）に置き、[監視コア](monitor-core.md)のスナップショットとイベントだけを使う。

## 1. トレイアイコン

優先度の高い順に1つを表示する。

| 状態 | アイコン | ファイル | 条件 |
|---|---|---|---|
| 要確認 | 赤に「!」 | `attention.png` | 未確認の `Failed` または `Orphaned` がある |
| 実行中 | 青に件数 | `running-1.png` 〜 `running-9.png`、10件以上は `running-9plus.png` | `Running` / `Queued` / `Quiet` が1件以上 |
| 完了 | 緑 | `done.png` | 未確認の `Completed` がある |
| 待機 | 灰色 | `idle.png` | 上記のどれでもない |

- アイコンは `src-tauri/icons/tray/` に描画済みのPNG（32px）を置いてある。実行時に文字を描くことはせず、`include_bytes!` でバイナリに埋め込む（実行ファイルの場所に左右されないようにするため）。
- 「未確認」は、そのジョブを確認済みにしたら解除する。確認済みにするきっかけは、トレイのメニューからそのジョブを選んだとき、と画面でそのジョブを表示したとき（画面の段階で `mark_seen` コマンドを作る）。
- 未確認の情報はメモリ上にだけ持つ。本アプリを再起動したら、すでに終わっていたジョブは確認済みとみなす。
- 未確認になるのは、本アプリの起動後に `StateTransition` で `Completed` / `Failed` / `Orphaned` になったジョブだけとする。

## 2. ツールチップ

「Codex: 2件実行中（GitManager: 検証中 12分 / MonitoringAI: 編集中 3分）」のように出す。実行中が0件なら「Codex: 待機中」。

- Windowsのツールチップは文字数に上限（127文字）があるので、超える場合は後ろのジョブから削って「ほか N件」とする。
- フェーズの表示名は[データソース仕様 4](data-source.md#4-phase-の値)の「表示（案）」を使う。`Quiet` は「応答なし？」、`Queued` は「待機中」とする。
- 経過時間の表示: 1分未満は「1分未満」、60分未満は「N分」、それ以上は「N時間M分」。

## 3. メニュー

上から順に次の項目を置く。

- 実行中のジョブ（最大5件、開始が新しい順）: `ワークスペース名「依頼の先頭」— フェーズ — 経過時間`。依頼の先頭は20文字まで（改行は空白に置き換え、切ったら「…」を付ける）。同じワークスペースで複数のジョブが動いていても見分けられるようにするため。依頼の先頭が無いときは「」ごと省く。選ぶとウィンドウを開き、そのジョブを確認済みにする。6件以上あるときは「ほか N件」（選べない項目）を足す。実行中が0件なら「実行中のジョブはありません」（選べない項目）
- 区切り線
- （プラグインのバージョンの不一致や読み込みエラーがあるときだけ）`⚠ <内容>`。選ぶとウィンドウを開く
- ウィンドウを開く
- 通知（チェック付き。設定の「通知全体」のオン・オフ）
- Windows起動時に起動（チェック付き）
- 区切り線
- 終了

**左クリック**でウィンドウを開く。右クリックでメニューを出す。

メニュー・アイコン・ツールチップは、`JobsChanged` / `StateTransition` / `HealthChanged` を受けたときと、**1分ごと**（経過時間を進めるため）に作り直す。

## 4. 通知

Windowsのトースト通知（`tauri-plugin-notification`）を使う。[監視コア](monitor-core.md#5-公開するインターフェース)の `StateTransition` をきっかけにする。

| きっかけ（`to`） | 既定 | タイトル | 本文 |
|---|---|---|---|
| `Running`（`from` が `None` / `Queued` のとき） | オフ | Codexが開始 | `<ワークスペース> — <依頼の先頭>` |
| `Completed` | オン | Codexが完了 | `<ワークスペース> — <要約の先頭>` |
| `Failed` | オン | Codexが失敗 | `<ワークスペース> — <errorMessage の先頭>` |
| `Orphaned` | オン | Codexのジョブが停止した可能性 | `<ワークスペース>` |
| `Quiet` | オフ | Codexが応答していません | `<ワークスペース>（N分）` |

- 本文の「先頭」は80文字まで。改行は空白に置き換える。
- 本アプリの起動時に、すでに終わっていたジョブは通知しない（`StateTransition` は最初の読み込みでは出ない）。
- 監視中に新しく現れたジョブは `from: None` の `StateTransition` で届く。現れた時点で `Completed` / `Failed` なら、それぞれの通知を出す。
- `Quiet` → `Running` のように、実行中の状態どうしで行き来したときは「開始」の通知を出さない。
- オン・オフは全体と、きっかけごとに設定できる（[アプリの土台 3](app-shell.md#3-設定)）。
- **通知のクリックでジョブを開く機能は、段階1では入れない。** `tauri-plugin-notification` はデスクトップでクリックなどの操作を受け取れない（タイトル・本文・アイコン・音だけが使われる）ため。ジョブを開くにはトレイを使う。必要になったら、WinRTのトースト通知を直接使う方法を検討する（[DESIGN.md 8](../DESIGN.md#8-未決事項)）。
- 開発ビルド（`target\debug` / `target\release` から起動）では、プラグインがアプリIDを設定しないため、通知の送り主の表示がアプリ名にならない。インストールしたアプリでは正しく表示される。

## 5. 実装の取り決め

- **表示を決める処理は、Tauriに依存しない純粋な関数**にまとめる（例: `src-tauri/src/presentation.rs`）。対象: アイコンの選択、ツールチップの文面と省略、メニューの項目の並び、通知を出すかの判定と文面、フェーズの表示名、経過時間の表示。入力はジョブの一覧（`JobSummary`）、未確認の集合、設定、現在時刻とし、Tauriの型を使わない。
- Tauri側（`tray.rs`、`notify.rs` など）は、純粋な関数の結果をトレイと通知に反映するだけの薄い層にする。
- 監視コアのイベントは、専用のスレッドで受け取る（[アプリの土台 5](app-shell.md#5-監視コアとのつなぎ方)）。

## 6. テスト

- 5の純粋な関数を単体テストする。最低限: 同じワークスペースのジョブが2件あるときのメニューの項目（依頼の先頭で見分けられること）、アイコンの優先度（要確認＞実行中＞完了＞待機）、件数の「9+」、ツールチップの省略、メニューの「ほか N件」、通知のきっかけの表（`from: None` を含む）、設定でオフにした通知が出ないこと、改行と長い文字列の扱い、経過時間の境目（59秒・60分）。
- 実際のトレイと通知の表示は、手動の受け入れ確認で確かめる（[DESIGN.md 7](../DESIGN.md#7-段階1の受け入れ基準)）。
