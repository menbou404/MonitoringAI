# 画面とRust・画面間のやり取り

- 対象: 段階1
- 最終更新: 2026-10-09
- 前提として読む文書: [監視コア](monitor-core.md)、[データソース仕様](data-source.md)、[ジョブの文脈](job-context.md)、[履歴](history.md)、[アプリの土台](app-shell.md)、[トレイと通知](tray-notification.md)
- 前提: Codexのジョブは、**同じワークスペースでも別のワークスペースでも、複数が同時に動く**。一覧も詳細も、同時に何件動いていても見分けられるようにする。

ジョブの一覧と詳細を見る画面（React + TypeScript + Vite、`src/`）と、Rustとのやり取りの取り決め。ウィンドウの作成と破棄は[アプリの土台 2](app-shell.md#2-ウィンドウの寿命)を参照。

## 1. 画面の構成

1つのウィンドウを左右に分ける。左がジョブ一覧（幅360px固定）、右が詳細。画面の言語は日本語。ライト／ダークテーマはOSの設定に従う（`prefers-color-scheme`）。

│ [バナー: プラグインのバージョン未確認 / 読み込みエラー]            │
├──────────────────────┬───────────────────────────────────────────┤
│ [ワークスペース▼] ⚙  │ Codexに段階4を実装させる                    │
│ ▼ GitManager の MCP… │ GitManager の MCP 設計 · GitManager · rescue│
│  ● Codexに段階4を…12分│ 実行中（検証中）· 開始 10:02 · 12分         │

│    検証中 · cargo t… │ ▸ 依頼の全文                               │
│    ↳ 前回: 段階3 · 完了│                                           │
│  ● READMEの誤字修正 3分│ ┌ ログ ─────────────────────────────┐    │
│    GitManager · RE…  │ │ 10:02:25 Thread ready (…)         │    │

### 1.1 ジョブ一覧（左）

一覧は **会話 → 依頼（ジョブ） → 地続きの前回以前のジョブ** の階層で見せる（[ADR-0004](../adr/0004-job-context-and-history.md)、[ジョブの文脈](job-context.md)）。

```
[ワークスペース▼] ⚙
▼ Codex実行状況の監視アプリ          実行中 1
   ● Codexに画面の実装を依頼            12分
     MonitoringAI · 画面（ジョブ一覧・詳細…
     検証中 · Running command: npm test
   ✓ Codexに監視コアの修正を依頼   10/04 12:33
     ↳ 前回: Codexに監視コア実装を依頼 · 完了
▶ GitManager の MCP 設計              （完了 3）
▼ 会話が不明 — OtherWork
   ✓ ログ表示の仮想スクロールが…    14:37
```

- 上部: ワークスペースの絞り込み（「すべて」＋現れたワークスペース名）と、設定を開くボタン（⚙）。
- 対象: 実効状態が `Queued` / `Running` / `Quiet` / `Orphaned` のジョブ全部と、それ以外で終了（無ければ作成）が設定の期間内（既定3日）のもの。
- **第1階層: 会話**（`context.sessionId` ごと）
  - 見出し: 会話のタイトル（無ければ「名前のない会話」）。右に「実行中 N」、または折りたたみ中なら「（完了 N）」のような件数。
  - 文脈が無いジョブ（`context` が `null`）は、ワークスペースごとに「会話が不明 — <ワークスペース名>」という会話としてまとめる。
  - 並び順: 実行中のジョブがある会話を先に（その中の最新の開始が新しい順）、その後は最後の活動（終了または作成）が新しい順。
  - 折りたたみ: 実行中または未確認のジョブがある会話は開く。それ以外は閉じる。利用者が開閉したら、ウィンドウを閉じるまで覚えておく。
- **第2階層: ジョブ**（同じスレッドのジョブは、最新のものだけをこの階層に出す）
  - 1段目: 状態アイコン、**依頼の説明**（`context.requester.description`。無ければ `promptHead`、それも無ければ `title`）、右端に経過時間（実行中）または終了時刻。未確認なら先頭に点。`kindLabel` が `rescue` 以外なら小さく出す。`requester.depth` が2以上なら「（<parentDescription> から）」を薄く添える。
  - 2段目: 薄い文字で、ワークスペース名 · 依頼文の先頭（`promptHead`。1段目が依頼文の先頭なら省く）。
  - 3段目: 実行中ならフェーズの表示名と `latestMessage`。終わったものは出さない（2段にする）。
  - **同じ会話・同じワークスペースのジョブが並んでも、1段目の依頼の説明で見分けられるようにする。**
- **第3階層: 地続きの前回以前のジョブ**（`previousJobId` をたどったもの）
  - 第2階層の行の下に、1行で「↳ 前回: <依頼の説明> · <状態の表示名>」を新しい順に出す。3件を超えたら「ほか N件」で畳み、押すと全部出す。
  - 選ぶと、そのジョブを詳細に出す。
- 状態アイコンと表示名:

  | 実効状態 | アイコン | 表示名 |
  |---|---|---|
  | `Queued` | ○（青） | 待機中 |
  | `Running` | ●（青） | フェーズの表示名（[データソース仕様 4](data-source.md#4-phase-の値)） |
  | `Quiet` | ●（橙） | 応答なし？ |
  | `Orphaned` | ！（赤） | 停止した可能性 |
  | `Completed` | ✓（緑） | 完了 |
  | `Failed` | ✕（赤） | 失敗 |
  | `Cancelled` | －（灰） | キャンセル（`archivedNote` があれば「中断された可能性」） |
  | `Unknown` | ？（灰） | `status` の値をそのまま |

- 選んだ行が詳細に出る。↑↓キーで、見えている行（会話の見出しを除く）の間を選択が動く。←→キーで会話を閉じる・開く。
- 一覧は仮想スクロール（`@tanstack/react-virtual`）で描く。会話の見出しも1行として扱う。
- ジョブが1件も無いときは「Codexのジョブはまだありません」と、監視中の状態ルート（`health.watchedRoots`）を出す。
- 経過時間は30秒ごとに描き直す。表示の仕方はトレイと同じ（1分未満は「1分未満」、60分未満は「N分」、それ以上は「N時間M分」）。

### 1.2 詳細（右）

- 何も選んでいないときは「左の一覧からジョブを選んでください」。
- 見出し: **依頼の説明**（無ければ依頼文の先頭）、その下に会話のタイトル · ワークスペース名 · 種別、状態の表示名、開始時刻と経過時間（終了していれば所要時間と終了時刻）、`write` が真なら「書き込みあり」。依頼したものが入れ子なら「<parentDescription> から依頼」、会話の本体から直接なら「会話から直接依頼」と添える。
- 地続き: `previousJobId` があれば「前回: <依頼の説明>」、このジョブを前回とするジョブがあれば「次回: <依頼の説明>」を出し、押すとそのジョブに移る。
- **履歴にだけあるジョブ**（`archived`）: 上部に「codex-plugin-cc の一覧から消えたジョブです（Claude の会話が終わると消えます）。ログは表示できません。」と出し、`archivedNote` があれば添える。ログの欄は出さず、依頼文は `promptHead`（先頭200文字）だけを出す。
- 依頼の全文（`prompt`）: 折りたたみ式。最初は閉じる。
- **ログ**:
  - ログを1行の形式とブロックの形式（[データソース仕様 7](data-source.md#7-ログファイルの形式)）に分けて表示する。時刻はローカル時刻の `HH:mm:ss`。
  - `Running command:` / `Command completed:` / `Command failed:` の行は等幅。`Command failed:` は赤。
  - `Assistant message` と `Final output` のブロックは、左に色の帯を付けて目立たせ、本文は折り返して全文を出す。
  - リアルタイムで追記する。末尾にいる間は自動でスクロールし、上にスクロールしたら止める。止まっている間に追記があったら「新しいログ ↓」ボタンを出す。
  - 最初は末尾の 1MB だけを読む。それより前があれば（`truncatedBefore`）、先頭に「さらに読み込む」ボタンを出し、押すと直前の1MBを読み足す。
  - ログが長くなるので仮想スクロールで描く（行の高さが違うので、要素の高さを測る方式にする）。
- 結果: 完了・失敗・キャンセルしたら、ログの上に結果の欄を出す。`Completed` なら `summary`（`state.json` 側）と `rendered`、`Failed` / `Cancelled` なら `errorMessage`。`rendered` は等幅のまま、折り返して出す（Markdownとして描画しない）。
- 操作: 「フォルダを開く」（ワークスペース）、「ログを開く」（ログファイルを既定のアプリで開く）、「IDをコピー」（ジョブIDとthreadIdを選べる）。コピーは `navigator.clipboard` を使う。
- 詳細を表示したら `mark_seen` を呼ぶ。

### 1.3 上部のバナー

`health.lastError` があればそれを、`pluginVersion` があって `versionSupported` が偽なら「codex-plugin-cc のバージョン（X）は動作未確認です」を出す。どちらも無ければバナーごと出さない。

### 1.4 設定（⚙）

ダイアログで開く。保存したら即座に反映する。

| 項目 | 入力 | 範囲 |
|---|---|---|
| 通知（全体） | スイッチ | |
| 通知のきっかけ（開始・完了・失敗・停止した可能性・応答なし） | スイッチ×5 | |
| 応答なしと判定するまでの分数 | 数値 | 1〜120 |
| 一覧に出す終わったジョブの期間（日） | 数値 | 1〜30 |
| 履歴の保存期間（日） | 数値 | 1〜90。一覧の期間以上 |
| 追加で監視する状態ルート | 1行に1つのテキスト | 絶対パスだけ。空行は無視 |
| Windows起動時に起動 | スイッチ | |

範囲外の値は保存できないようにし、その欄の下に理由を出す。Rust側でも同じ範囲を検証し、外れていたらエラーを返す。

## 2. コマンド（画面 → Rust）

| 名前 | 引数 | 戻り値 | 内容 |
|---|---|---|---|
| `get_snapshot` | なし | `UiSnapshot` | `{ jobs: JobSummary[], unseen: string[], health: Health, settings: Settings }` |
| `get_job` | `id` | `JobDetail \| null` | 監視コアの `job_detail` |
| `read_log` | `id`, `from: number \| null` | `LogChunk \| null` | 監視コアの `read_log`。`from` が `null` なら末尾から1MB |
| `watch_log` | `id: string \| null` | なし | ログを購読するジョブを**1つだけ**指定する。前の購読は外す。`null` で外す |
| `mark_seen` | `id` | なし | 未確認から外し、トレイを更新し、`unseen-changed` を送る |
| `open_path` | `kind: "workspace" \| "log"`, `id` | なし | ジョブの `workspaceRoot` のフォルダ、またはログファイルを開く（`tauri-plugin-opener`） |
| `set_settings` | `Settings` | `Settings` | 検証して保存し、反映する（[アプリの土台 3](app-shell.md#3-設定)） |
| `take_pending_focus` | なし | `string \| null` | トレイから開かれたときに表示すべきジョブのIDを取り出す（取り出したら消える） |

- コマンドの中身は薄くし、処理は監視コアと本アプリの状態（`state.rs`）の関数に置く。
- `open_path` は、**本アプリが把握しているジョブのパスだけ**を開く。画面から任意のパスを受け取らない。ログファイルは `logFile` ではなく、状態ディレクトリと `id` から組み立てたパスを使う（監視コアと同じ）。
- エラーは日本語の文字列で返し、画面は詳細の上部に出す。
- ウィンドウが破棄されたら（`WindowEvent::Destroyed`）、ログの購読を外す。

## 3. イベント（Rust → 画面）

| 名前 | 内容 |
|---|---|
| `monitor-event` | 監視コアの `MonitorEvent` をそのまま送る（`type` で種類を見分ける。実装済み） |
| `unseen-changed` | `string[]`。未確認のIDの集合が変わったときに全体を送る |
| `settings-changed` | `Settings`。トレイのメニューなど、画面の外で設定が変わったとき |
| `focus-job` | `{ id }`。ウィンドウがすでに開いているときに、トレイのメニューからジョブが選ばれたら送る |

### トレイからジョブを指定して開く流れ

ウィンドウは開くたびに作り直されるので、画面の準備ができる前に送ったイベントは届かない。そこで次のようにする。

1. トレイのメニューでジョブが選ばれたら、本アプリの状態に「表示待ちのジョブ」としてIDを記録する。
2. ウィンドウがすでに開いていれば、`focus-job` を送り、記録を消す。
3. 新しく作ったウィンドウでは、画面が起動時に `take_pending_focus` を呼んで取り出し、そのジョブを選ぶ。

画面は起動時に、`get_snapshot` → `take_pending_focus` の順に呼び、その後でイベントの受け付けを始める。`get_snapshot` とイベントの間で取りこぼしが出ないよう、受け付けを始めた直後にもう一度 `get_snapshot` を呼んで置き換える。

## 4. 画面の作り

```
src/
├─ main.tsx              起動
├─ App.tsx               全体の配置
├─ api.ts                コマンドとイベントの型付きの呼び出し口（invoke / listen はここだけで使う）
├─ bindings/             ts-rs が生成した型（手で編集しない）
├─ model/
│  ├─ format.ts          フェーズ・実効状態の表示名、経過時間、時刻の表示（純粋な関数）
│  ├─ logParse.ts        ログの解析（1行・ブロック・コマンド行の判定。純粋な関数）
│  ├─ jobList.ts         グループ分け、並べ替え、絞り込み（純粋な関数）
│  └─ store.ts           スナップショットとイベントから画面の状態を作る reducer（純粋な関数）
├─ components/           JobList / JobRow / JobDetail / LogView / Banner / SettingsDialog など
└─ styles.css            CSS変数で配色を定義し、ダークテーマは prefers-color-scheme で切り替える
```

- 状態管理のライブラリは使わず、React の `useReducer` と `store.ts` の reducer で持つ。
- UIの部品ライブラリは使わない（バンドルを小さく保つ）。
- フェーズの表示名と経過時間の表示は、Rust側（`presentation.rs`）と同じ規則にする。両方のテストで同じ例を確かめる。

## 5. 型

画面に渡す型は Rust 側で定義し、`ts-rs` で TypeScript の型を生成する。手で二重に書かない。

- 生成先は `src/bindings/`（`src-tauri/.cargo/config.toml` の `TS_RS_EXPORT_DIR` で指定済み）。
- 生成は `npm run bindings`（`ts` 機能付きで `export_bindings` のテストを動かす）。**生成した型はリポジトリに入れる**（Rustをビルドしなくても画面をビルドできるように）。
- 対象: 監視コアの `JobSummary` / `JobDetail` / `EffectiveState` / `LogChunk` / `Health` / `MonitorEvent`、本アプリの `UiSnapshot` / `Settings`（とその中の型）。各型に `#[cfg_attr(feature = "ts", derive(ts_rs::TS), ts(export))]` を付ける。
- **`u64` / `i64` のフィールドには `#[cfg_attr(feature = "ts", ts(type = "number"))]` を付ける。** ts-rs は既定で `bigint` にするが、JSONでは数値として届くため。ログのバイト位置などは 2^53 を超えない。
- 日時（`chrono::DateTime<Utc>`）は文字列（ISO 8601）として届く。

## 6. テスト

- Vitest で `model/` の純粋な関数を試す。最低限:
  - `format.ts`: フェーズ・実効状態の表示名（知らない値を含む）、経過時間の境目（59秒・60分）
  - `logParse.ts`: 1行の形式、ブロックの形式（空行・複数行の本文）、コマンド行の判定、途中で切れた最後の行
  - `jobList.ts`: 会話ごとのまとめ（文脈が無いジョブの「会話が不明 — <ワークスペース>」を含む）、会話とジョブの並び順、地続きのジョブを最新の1件にまとめて前回以前を下に付けること（3件の連鎖）、表示期間、ワークスペースの絞り込み、折りたたみの既定、**同じ会話・同じワークスペースの実行中ジョブが2件あるとき、依頼の説明で別の行として出ること**、依頼の説明が無いときの代わり（`promptHead` → `title`）
  - `store.ts`: `monitor-event` の各種類の反映（`JobsChanged` の追加・削除、選択中のジョブが削除されたとき）、`unseen-changed`、`LogAppended` の連結（`start` が手元の末尾と一致しないときは読み直す）
- Rust 側: 表示待ちのジョブの記録と取り出し、`watch_log` の置き換え、`open_path` が把握していないIDを拒むこと、設定の検証（範囲外の値）を単体テストする。
- 画面の見た目と操作は、手動の受け入れ確認で確かめる（[DESIGN.md 7](../DESIGN.md#7-段階1の受け入れ基準)）。
