# フォーカスガード

- 対象: 段階2
- 状態: **凍結**（2026-10-13）。P2・P3の結果と凍結の理由は [7. P2の結果と凍結](#7-p2の結果と凍結) にある
- 最終更新: 2026-10-13
- 前提として読む文書: [データソース仕様 6. プロセスの構造](data-source.md#6-プロセスの構造)
- 関連: [ADR-0003](../adr/0003-focus-interruption-strategy.md)（3層で防ぐ方針。この機能は「受け身の防御」の層）

Codexの作業中に、ユーザーが操作していないのに別のウィンドウがフォーカスを奪ったら、取り返す機能。**AIが指示を守らなくても効く**ことが、この機能の役目である。

## 1. P3で分かったこと

当初は「前面に来たウィンドウのプロセスから親をたどり、ブローカーかジョブの pid に行き着けばCodexが起動したものとみなす」つもりだった。P3で調べた結果、この方法では**実際に起きたフォーカスの奪われ方を1つも捕まえられない**ことが分かった。

| 経路 | 実際の動き | 親をたどる方法で捕まえられるか |
|---|---|---|
| Codexがコマンドとして起動したアプリ | サンドボックス（`unelevated`）の下で、同じユーザー・同じセッション・整合性レベル Medium の**制限付きトークン**で動き、ジョブオブジェクトに入る。ウィンドウは **`CodexSandboxDesktop-<ID>` という専用の見えないデスクトップ**に作られ、ユーザーの `Default` デスクトップには出ない | 捕まえる必要が無い（そもそもフォーカスを奪わない） |
| Codexが呼び出すMCPサーバー | サンドボックスの外で動く。MCPのツールが、既に起動している別のアプリ（例: 開発中のアプリの常駐プロセス）に働きかけ、そのアプリのウィンドウが前面に出る | 捕まえられない。前面に出たウィンドウの持ち主は、Codexの配下にいない |
| Codexの画面操作機能（computer use） | サンドボックスの外で動き、組み込みブラウザやユーザーのブラウザでページを開く | 捕まえられない。ブラウザはCodexの配下にいない |

- 実際の事例（GitContextの開発中）では、MCPのテスト用ツールを呼んだ時期に、既に動いていたGitContextのメイン画面が前面に出ていた。コマンドとしてアプリを直接起動した記録や、サンドボックスの外での実行を求めた記録は無かった。
- 調べ方: 依頼文の中でウィンドウを開くコマンドをCodexに実行させ、そのプロセスの親子関係・トークン・ウィンドウを本アプリと同じ権限で観察した。あわせて、Codexの過去の実行記録から、呼ばれたツールの名前とコマンドの先頭だけを集計した。

## 2. 判定方法

「誰が起動したか」ではなく、**「ユーザーが操作していないのに前面が切り替わったか」**で判定する。

- `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` で前面の切り替わりを受け取る。
- 低レベルのマウス・キーボードのフック（`WH_MOUSE_LL` / `WH_KEYBOARD_LL`）で、切り替えの理由になる操作の時刻を記録する。
  - 理由とみなす操作: 新しく前面に来たウィンドウ（またはタスクバー・Alt+Tab の画面）へのクリック、Alt+Tab、Winキー、Win+数字などの切り替え用のショートカット。
  - 理由とみなさない操作: 文字の入力。入力中に奪われる場合こそ捕まえたいので、ただのキー入力では「ユーザーが切り替えた」と判断しない。
- 直前の一定時間（P2で決める）に理由となる操作が無い切り替えを「奪われた」とみなす。
- **Codexのジョブが `running` の間だけ**働かせる。監視コアの状態をそのまま使う。
- 次のものは対象外にする。
  - 本アプリ自身のウィンドウ、シェル（タスクバー、スタートメニュー、通知）。
  - 例外として登録したアプリ。例: 確認のために前面に出てきてほしいウィンドウ（GitContextの確認ウィンドウなど）。
- 1つの切り替えを、どのジョブが起こしたかは分からない。表示では「Codexの作業中に」とだけ言い、動いているワークスペースの名前を添える。

## 3. 対処

P2の結果で決める。候補は次の2つ。
- 元のウィンドウを手前に戻す（`SetForegroundWindow`。前面ロックの制限がある）
- 前面に来たウィンドウを最小化する（`ShowWindow(SW_MINIMIZE)`）。元のウィンドウにフォーカスが戻るかは、Windowsの動き次第

仮想デスクトップへ移す方法は、非公開APIに頼るので採らない。

## 4. 切り替えと表示

- トレイのメニューからオン・オフする。アプリごとの例外を設定で持つ。
- 取り返したら、トレイに「Codexの作業中に <アプリ名> が前面に出たため、元に戻しました」のように出す。例外への追加をそこから選べるとよい。

## 5. 実装の置き場所

Win32の処理（フック、ウィンドウ操作）は、新しいクレート（例: `focus-guard`）に閉じ込める。監視コアからは、`running` のジョブがあるかどうかと、そのワークスペースの名前だけを受け取る。

## 7. P2の結果と凍結

### P2で分かったこと

実験用の「奪う役」（Tauriと同じ方法で前面に出るプログラム）、文字を打つ「入力先」、判定と取り返しを行う「見張り役」を、それぞれ別のプロセスで動かして確かめた（2026-10-13）。

| 項目 | 結果 |
|---|---|
| 判定（誤判定） | 普段の切り替え（クリック、Alt+Tab、タスクバー、スタートメニュー、リンク、最小化）28回を、すべてユーザーの操作と判定した |
| 判定（検知） | 奪われてから約10ミリ秒で気づき、正しく判定した。前のウィンドウが閉じた・最小化されたあとにWindowsが次のウィンドウを前面に出す動きは、「奪われた」から除く必要がある |
| 奪われたときの被害 | 奪われている間に打った文字は、すべて奪った側に流れる（4秒で最大31文字） |
| 前面ロック | 何もしないアプリは前面に出られない。ただし、Altキーを押したことにする裏技（Tauriの窓の部品 tao の `force_window_active`。`set_focus` で使われる）で、確実にすり抜けられる |
| 取り返し | `SetForegroundWindow` だけでは前面ロックに止められる。入力の仕組みをつなげる方法（`AttachThreadInput`）と、奪ったウィンドウを最小化する方法は、成功すれば約15ミリ秒で戻せ、流れる文字は0〜1文字。ただし、奪う側が続けて前面に出ようとすると奪い返されることがあり、戻した後も見張ってやり直す必要がある |
| Altの裏技の副作用 | 偽のAltがユーザーのウィンドウに届くと、メニュー操作の状態になり、その後に打った文字が吸い込まれる。低レベルのキーボードフックで偽のAlt（`LLKHF_INJECTED`）を握りつぶすと、この副作用は消えた |
| 予防 | 偽のAltを握りつぶしても、奪われるのは防げなかった。前面ロックは、偽のキーが送られた時点で（フックに届く前に）外れる |

### 先行事例

- Windows全般では、全プロセスにDLLを入れて `SetForegroundWindow` を無効にする道具（Stay Focused。作者自身が実験的なベータ版としている）と、マウス操作なしの前面の切り替えを認めない道具がある。前者は確実だが、全アプリに手を入れるので常駐アプリには入れない。後者は2の判定方法と同じ考え方である。
- Codex本体にも、Windowsでフォーカスを奪う不具合の報告が多数ある（コマンドのたびにコンソール画面が出る、組み込みブラウザを開くとCodexのアプリが前面に出る、など）。
- AIの作業と結びつけてフォーカスを守る道具は見つからなかった。

### 凍結の理由

- 実際の被害は、前面を奪う側のアプリの作りから来ていた。開発中のアプリなら、そのアプリ側で直すのが根本の対策になる。たとえば、AIからの確認要求で `set_focus` を呼ばずにタスクバーの点滅だけにする、などである。
- Codexがコマンドとして起動したアプリは、見えないデスクトップで動くので、もともとフォーカスを奪わない。本アプリの開発中にフォーカスを奪われなかったのは、このためと、AIの操作で前面に出る仕組み（確認ウィンドウなど）が本アプリに無いためである。
- 取り返しは可能だが、確実にするには奪い返しへの対処などの作り込みが要り、得られる効果に見合わない。

### 再開するときの出発点

- 判定は2の方法でよい。加えて、直前のウィンドウが閉じた・隠れた・最小化された直後（500ミリ秒以内）の切り替えは除く。
- 起動が重いアプリは、クリックから画面が出るまで1秒以上かかることがあり、判定の時間の幅（1秒）を超えて誤判定するおそれがある。「最後のクリックの後に文字を打っていなければ奪われたとみなさない」などの条件を検討する。
- 取り返しは、最小化か `AttachThreadInput` で行い、数百ミリ秒は見張り続けて、奪い返されたらやり直す。偽のAltの握りつぶしは、副作用の防止として併用する。
- 未決事項: Claude Code 自身の作業中（Codexのジョブが動いていないとき）も対象にするか。偽のAltを送る正当なツール（キーの割り当てを変えるツール、自動化ツール）への影響。
