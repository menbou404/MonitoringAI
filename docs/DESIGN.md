# MonitoringAI 設計書（全体像）

- 最終更新: 2026-10-04
- この文書には全体像と共通の取り決めだけを書く。機能ごとの詳細は [docs/design/](design/) の各文書に、技術選定の理由は [docs/adr/](adr/README.md) に書く。

アプリ名は **MonitoringAI**、アプリIDは **`com.menbou404.monitoringai`**。

---

## 1. 目的

Claude Code（Desktop版を含む）に codex-plugin-cc を入れ、設計をClaude、コーディングをCodexに分担させて開発している。このとき次の2つの問題がある。

1. **Codexの動きが見えない**。Claudeの画面からは、Codexが動いているのか、どのタスクを何の段階まで進めているのかがわからない。
2. **作業が中断される**。Codexが開発中のアプリを起動すると、ウィンドウが手前に出てフォーカスを奪い、ユーザーの作業が止まる。

Windowsのトレイに常駐するアプリで、この2つを解決する。

## 2. 段階

| 段階 | 内容 | 状態 |
|---|---|---|
| **段階1: 監視** | Codexジョブの一覧と状態の表示、ログのリアルタイム表示、トレイアイコンによる状態表示、完了・失敗の通知、ジョブの文脈（会話・依頼・地続き）と独自の履歴 | 確定 |
| PoC | 隠しデスクトップでのアプリ起動（P1）、フォーカスを取り返す方法（P2）、Codexが起動したプロセスの親子関係（P3） | 段階1と並行して実施 |
| **段階2: フォーカスガード** | Codexの作業中に、ユーザーの操作なしにフォーカスが奪われたら取り返す | **凍結**（P2・P3の結果。理由は[フォーカスガード 7](design/focus-guard.md#7-p2の結果と凍結)） |
| **段階3: 起動の窓口（MCP）** | Codexにアプリの起動・スクリーンショット・終了をさせるMCPツールと、起動ルール | 概要のみ |

### 対象外（段階1）

- Codexジョブを操作すること（キャンセル、再開など）。段階1は**読み取り専用**とする（[8. 未決事項](#8-未決事項)）。
- codex-plugin-cc を使わずにCodex CLIを直接使った場合の監視。
- macOS / Linux 対応。ただし、Windows固有の処理は限られたモジュールに閉じ込め、監視部分は移植しやすく保つ。

## 4. 用語

| 用語 | 意味 |
|---|---|
| ジョブ | codex-plugin-cc がCodexに渡した1件の作業（`/codex:rescue`、`/codex:review` など） |
| ワークスペース | ジョブを依頼したリポジトリ。プラグインはワークスペースごとに状態ディレクトリを分ける |
| 状態ルート / 状態ディレクトリ | プラグインが状態を書き出す場所（[データソース仕様 1・2](design/data-source.md#1-状態ルートの場所)） |
| ブローカー | プラグインがワークスペースごとに常駐させる中継プロセス（node）。配下で `codex app-server` を動かす |
| スレッド / ターン | Codex側の会話の単位（`threadId`）と、1回の依頼の単位（`turnId`） |
| 実効状態 | プラグインが書いた `status` に、プロセスの生存確認などを加えて本アプリが判定した状態（[監視コア 3](design/monitor-core.md#3-実効状態の判定)） |
| 未確認 | 終わったジョブのうち、まだ画面で表示していないもの。トレイアイコンの色に使う |

## 5. 全体の構成

### 5.1 構成図

```
┌─────────────── MonitoringAI.exe ───────────────┐
│ Rust（本体。常に動いている）                      │
│  ┌──── monitor-core（Tauriに依存しない）────────┐│
│  │ discovery → watcher → parser → store         ││
│  │              liveness ─┘  log_tail ─┘        ││
│  └──────────────────────┬───────────────────────┘│
│      スナップショット・変更イベント                │
│  ┌──────────────────────▼───────────────────────┐│
│  │ Tauri本体: tray / notify / settings / commands ││
│  └──────────────────────┬───────────────────────┘│
│                コマンド ↑↓ イベント                 │
│  ┌──────────────────────┴───────┐                 │
│  │ WebView2（画面。開いている間だけ存在）           │
│  │ React + TypeScript             │                 │
│  └──────────────────────────────┘                 │
└──────────────────────────────────────────────────┘
```

### 5.2 構成の原則

- **監視の処理は全部Rust側に置く。** 画面が閉じていても、トレイアイコンと通知が正しく動くようにするため。
- **監視ロジックは `monitor-core` クレートに分け、Tauriに依存させない。** テストしやすくするためと、段階3のMCPサーバー（別のexe）からも使えるようにするため。
- **画面は閉じたら破棄する。** メモリを抑えるため（[アプリの土台 2](design/app-shell.md#2-ウィンドウの寿命)、[ADR-0001](adr/0001-app-framework.md)）。
- **Windows固有の処理は限られた場所に閉じ込める。** 段階1では `monitor-core` の `liveness.rs` だけ。段階2以降は専用のクレートに置く。

### 5.3 リポジトリ構成

```
MonitoringAI/
├─ docs/                      設計書・ADR
├─ src/                       画面（React + TypeScript + Vite）
├─ src-tauri/
│  ├─ Cargo.toml              workspace
│  ├─ src/                    Tauri本体（トレイ、通知、設定、コマンド、常駐）
│  └─ crates/
│     └─ monitor-core/        監視コア
└─ package.json
```

### 5.4 主な依存

- Rust: `tauri` 2（`tray-icon` / `image-png` 機能）、`tauri-plugin-notification`、`tauri-plugin-single-instance`、`tauri-plugin-autostart`、`tauri-plugin-opener`、`notify` + `notify-debouncer-full`、`serde` / `serde_json`、`chrono`、`thiserror`、`windows`、`tracing` / `tracing-subscriber` / `tracing-appender`、`ts-rs`（型の自動生成）
- 画面: React、TypeScript、Vite、仮想スクロールのライブラリ1つ、Vitest

これ以外の依存を足すときは、理由を設計書に書く。

## 6. 共通方針

- **読み取り専用**: 状態ディレクトリと `.codex` の下には一切書き込まない。ファイルは、プラグイン側の書き込みや削除を妨げない共有モードで開く。
- **ネットワーク**: 一切使わない。
- **プライバシー**: 依頼の内容やCodexのログの本文は、画面に表示するだけにする。本アプリのログには書き出さない（IDと件数まで）。Codexの実行記録に含まれるアカウントの識別子は扱わない。
- **非公開の内部形式への依存**: 知らないフィールドや値があっても落ちないように作る（[データソース仕様 8](design/data-source.md#8-互換性の扱い)）。
- **テストのデータ**: 実ファイルは依頼の内容やアカウント情報を含むので、リポジトリに入れない。fixtureは実ファイルの構造を写した**架空のデータ**で作る。
- **テストの分担**: 各機能のテストは、それぞれの文書の「テスト」の節に書く。機能をまたぐ確認は [7章](#7-段階1の受け入れ基準)で行う。

## 7. 段階1の受け入れ基準

実際に `/codex:rescue --background` を2つのワークスペースで同時に動かして、手動で確かめる。

1. 2つのワークスペースで同時に動いているジョブと、**同じワークスペースで同時に動いている2つのジョブ**が、どれも見分けられる形で一覧とトレイのメニューに出る。フェーズと経過時間が、ログの進み具合から**2秒以内**に追従する。
2. 詳細でログがリアルタイムに追記される。
   - **実行中の画面**: ウィンドウを開くと動いているジョブだけがカードで並び、フェーズ・経過時間・「動き N前」・最新のメッセージが5秒以内に追従する。同じ会話のジョブが7件以上あっても、「ログ」の一覧は完了したジョブが畳まれて短く保たれる。
3. 完了・失敗の通知が出る。トレイのメニューから実行中のジョブを選ぶと、ウィンドウが開く。
4. Codexが動いている間、Claude Codeのプロセスを強制終了すると、5〜10秒以内に `Orphaned` になる。
5. トレイアイコンが [トレイと通知 1](design/tray-notification.md#1-トレイアイコン) のとおりに変わる。
6. **常駐時のメモリ**: ウィンドウを閉じた状態で、本アプリのプロセスの合計（WebView2の子プロセスを含む）を測り、[ADR-0001](adr/0001-app-framework.md) に記録する。目標はプライベートワーキングセットで **30MB以下**。ウィンドウを閉じたら WebView2 のプロセスが残らないことも確かめる。
7. **待機中の負荷**: Codexのジョブが動いていない間、本アプリのCPU使用時間が1分あたり1秒未満（1コアの2%未満）であること。
8. **文脈**: 実際の Claude の会話から依頼したジョブが、その会話のタイトルの下に、サブエージェントの説明（依頼の説明）で表示される。`--resume` で続きを頼んだジョブが、前回のジョブとつながって表示される。
9. **履歴**: Claude の会話を終えてプラグインがジョブを消しても、一覧に残り、結果の要約と最終出力を見られる。
10. プラグインの動作に影響しない。本アプリを動かしたまま、ジョブの作成・キャンセル・51件以上による削除が正常にできる。

## 8. 未決事項

| 項目 | 内容 |
|---|---|
| `sessionId` からClaudeのセッション名を出す | Claude Code CLIの記録（`~/.claude/projects/*/<sessionId>.jsonl`）との対応は取れそうだが、Desktop版でのセッション名の取り方は未調査 |
| ジョブの操作 | キャンセルを付けるなら、プラグインの `codex-companion.mjs cancel <jobId>` を呼ぶのが安全。読み取り専用の原則を崩すので、段階1の後に判断する |
| 補助データの利用 | Codexの実行記録からのトークン数などの表示（[データソース仕様 9](design/data-source.md#9-補助データ段階1では使わない)） |
| 配布 | インストーラー（NSIS / MSI）を作るか、署名をどうするか |
| 通知のクリックでジョブを開く | `tauri-plugin-notification` はデスクトップでクリックを受け取れない。WinRTのトースト通知を直接使えば実現できる見込みだが、アプリIDの登録（インストール）が前提になる（[トレイと通知 4](design/tray-notification.md#4-通知)） |

機能ごとの未決事項は、各文書の「未決事項」の節に書く。
