# ADR-0003: 作業の中断は「指示・受け身の防御・正規の起動手段」の3層で防ぐ

- 状態: 承認（各層の具体的な方式は、PoCの後に「結果の記録」へ追記する）
- 日付: 2026-10-04

## 背景

Codexは、開発中のアプリの動作を確かめるために、そのアプリを何度も起動する。起動したウィンドウが手前に出てフォーカスを奪うので、ユーザーの作業（入力など）が中断される。

制約:
- 利用環境は **Windows 11 Home**。Windows Sandbox、Hyper-V、自分自身へのリモートデスクトップ接続が使えない。そのため、VMや別のセッションでアプリを隔離して動かす手軽な方法がない。
- AIへの指示（`AGENTS.md` や依頼文）は、守られないことがある。

## 検討した選択肢

| 選択肢 | 効果 | 問題 |
|---|---|---|
| 1. AIへの指示だけ（「GUIを起動するな。テストやビルドで確かめよ」） | 大部分は防げる。費用もかからない | 守られないことがある。GUIでしか確かめられない動作を確かめられなくなる |
| 2. 開発中のアプリに「静かに起動するモード」を入れる（環境変数でウィンドウを非表示・フォーカスなし・画面外に） | 確実 | アプリごとに仕込みが必要。AIがその変数を付け忘れると効かない |
| 3. 隠しデスクトップで起動する（`CreateDesktop`） | ウィンドウが一切見えず、フォーカスも奪わない | WebView2 などのGPU描画が動くか未確認。AIがこの方法を使わなければ効かない |
| 4. フォーカスガード（フォーカスを奪われたら取り返す。判定方法はP3の後に改めた） | **AIが協力しなくても効く** | 一瞬ちらつく。入力中の数文字が向こうに流れる可能性がある。Windowsの前面ロックの制限がある |
| 5. VM / Windows Sandbox / 別のユーザーセッション | 完全に隔離できる | Home版では使えない。重い |

## 決定

1つの方法には頼らず、**役割の違う3層を組み合わせる**。

| 層 | 中身 | 位置付け |
|---|---|---|
| **① 指示**（選択肢1、できれば2） | Codexに「GUIを起動しない。確かめるならMCPの起動ツールを使う」と指示する | 本アプリの外での運用。最初に行う |
| **② 受け身の防御**（選択肢4） | フォーカスガード。AIが指示を破っても効く | **防御の本体**。段階2 |
| **③ 正規の起動手段**（選択肢3、ダメなら画面外への配置） | 本アプリがMCPツール（`launch_app` / `screenshot` / `close_app`）を提供し、見えない場所でアプリを起動してスクリーンショットをAIに返す | 「禁止する」代わりに「この方法で確かめて」と道を用意する。段階3 |

### 理由

1. **AIへの指示は破られることがある**ので、指示に頼らない層（②）が必要になる。
2. 禁止するだけだと、AIはGUIの動作を確かめられず、作業の質が下がる。③で安全な確かめ方を用意すれば、禁止する理由がなくなる。
3. ③だけでは強制できない（AIがコマンドを直接実行すれば迂回される）。だから②と必ず組み合わせる。
4. ②と③は、本アプリの監視機能がすでに把握している情報（どのジョブが、どのプロセスツリーで動いているか）をそのまま使う。だから、監視アプリに組み込むのが効率的である。「どのタスクが起動したか」を表示できるのも、組み込んだ場合だけの利点である。
5. Home版の制約で、選択肢5は使えない。

## 結果として受け入れること

- ②は「一度出てから取り返す」方式なので、一瞬のちらつきは避けられない。
- ③の「見えない場所での起動」は、PoC P1（[起動の窓口 2](../design/launch-mcp.md#2-poc)）の結果しだいで、画面外への配置などに後退する可能性がある。
- 任意のコマンドを起動できるMCPツールは危険なので、ワークスペースごとの許可リストで制限する。
- 段階が増える。段階1（監視）だけでも最初の問題は解決するので、段階2・3は段階1の後に着手する。
