# ADR-0002: codex-plugin-cc の状態ファイルを読み取り専用で監視する

- 状態: 承認
- 日付: 2026-10-04

## 背景

Codexの動き（どのタスクが、どの段階まで進んでいるか）を知る必要がある。Codexは codex-plugin-cc を通じて Claude Code から呼ばれる。そのため、情報の出どころの候補は複数ある。

## 検討した選択肢

| 選択肢 | 得られる情報 | 問題 |
|---|---|---|
| **A. プラグインの状態ファイル**（`state.json`、`jobs/*.json`、`jobs/*.log`） | ジョブ単位の状態、フェーズ、依頼内容、ワークスペース、進行ログ、PID、スレッドID | 非公開の内部形式で、バージョンアップで変わりうる |
| B. Claude Code のフック（`PreToolUse` / `PostToolUse` などでプラグインの呼び出しを捉える） | 呼び出しの開始と終了 | 途中のフェーズがわからない。バックグラウンド実行では開始しか捉えられない。利用者の設定ファイルを書き換える必要がある |
| C. プロセスの調査だけ（`codex.exe` などを探す） | 動いているかどうか | どのタスクか、何をしているかがわからない |
| D. Codexの実行記録（`~/.codex/sessions/**/rollout-*.jsonl`） | Codex側の詳細（ツール呼び出し、トークン数） | プラグインのジョブとしての状態（待機、キャンセルなど）がわからない。アカウント情報を含む |
| E. ブローカーの名前付きパイプに接続する | app-server のイベントを直接受け取れる | プラグインの通信に割り込むことになる。ブローカーは同時に1つの接続しか受け付けない作り（使用中のエラーコードがある）なので、**プラグインの動作を妨げるおそれがある** |

## 決定

**A を主な情報源とし、読み取り専用で監視する。** プロセスの情報（C）は、PIDの生存確認にだけ使う。D は必要になったら補助的に使う（段階1では使わない）。B と E は使わない。

### 理由

1. 監視に必要な情報（ジョブ単位の状態、フェーズ、依頼内容、ログ）が、Aだけで全部そろう。
2. プラグインは、フォアグラウンド実行でもバックグラウンド実行でも、同じ仕組み（`runTrackedJob`）で状態を書き出すことをソースで確認した。
3. 読み取り専用なので、プラグインにもCodexにも影響しない。利用者の設定を書き換える必要もない。
4. Bは情報が足りず、Eはプラグインの動作を妨げるおそれがある。

## 結果として受け入れること

- **非公開の内部形式に依存する。** 対策として次を行う（[データソース仕様 8](../design/data-source.md#8-互換性の扱い)）。
  - `installed_plugins.json` からプラグインのバージョンを読み、確認済みのバージョン以外では警告を出す。
  - `id` と `status` 以外のフィールドは任意とし、知らない値はそのまま表示する。
- **書き込み途中のファイルを読むことがある。** プラグインは一時ファイルを経由せずに直接上書きする。読み直しと、前回読めた内容の保持で対応する。
- **`status` だけでは本当に動いているかがわからない。** Claudeが異常終了すると `running` のまま残る。PIDの生存確認（使い回しの検証を含む）と、ログの更新時刻で補う（[監視コア 3](../design/monitor-core.md#3-実効状態の判定)）。
- プラグインを使わずにCodex CLIを直接使った場合は、監視できない。
