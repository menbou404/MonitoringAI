# ADR-0001: アプリの基盤にTauri 2（Rust + React/TypeScript）を使う

- 状態: 承認
- 日付: 2026-10-04

## 背景

MonitoringAI は、Codexの動きを監視し、Codexが起動したアプリによる作業の中断を防ぐ、Windowsのトレイ常駐アプリである（[設計書](../DESIGN.md)）。

アプリに求められる性質は次のとおり。

| 要件 | 重さ | 理由 |
|---|---|---|
| 常駐時のメモリが少ない | **最重要** | ほとんどの時間はトレイにいるだけで、開発作業の裏で常に動き続ける |
| Win32 APIを多く呼べる | 高 | ファイル監視、プロセスの調査、フォーカスの監視（`SetWinEventHook`）、隠しデスクトップ（`CreateDesktop`）など、OSを直接操作する処理が中心 |
| MCPサーバーを作れる | 中 | 段階3でCodexに起動の窓口を渡す |
| そこそこの画面を作れる | 中 | ジョブ一覧、リアルタイムのログ表示、設定 |
| 配布しやすい | 中 | exeを1つ置けば動くのが望ましい |
| 将来の移植の余地 | 低 | 監視部分はmacOSでも成り立つ。フォーカス対策はWindows固有 |

既存プロジェクトの知識や資産を流用できるかは、判断材料に**含めていない**。

## 前提: 画面の言語と本体の言語は別

どの選択肢でも、画面はHTML + TypeScriptか各フレームワーク独自のUIで書ける。しかし、Web技術の画面（WebView）はブラウザと同じく隔離されている。ファイルを自由に読む、プロセスを調べる、他のアプリのウィンドウを操作する、といったことはできない。

今回の中心はOSを直接操作する処理なので、**比較の本質は「本体を何の言語で書くか」と「常駐時にどれだけ軽いか」**にある。

用語:
- **WebView2**: Microsoft Edge（Chromium）の描画エンジンを、アプリに埋め込んで使うための部品。Windows 11には標準で入っている。Tauri はこれを使って画面を描く。

## 検討した選択肢

| 選択肢 | 本体 / 画面 | Win32の呼びやすさ | 常駐時のメモリ（目安） | 配布 |
|---|---|---|---|---|
| **A. Tauri 2** | Rust / HTML + TS | ◯ `windows` クレートで全APIを呼べる。`unsafe` が多く、やや冗長 | ◎ ウィンドウを破棄すればWebView2のプロセスごと消え、本体だけ（十数MB程度） | ◎ 数MBのexe。WebView2はOSに標準で入っている |
| B. C# / .NET（WPF / WinForms） | C# / XAML | ◎ P/InvokeやCsWin32で最も素直に書ける | ◯ ランタイムが常に載る（数十MB程度） | △ ランタイムを同梱すると数十MB以上。同梱しないと利用者がランタイムを入れる必要がある |
| C. Electron | Node.js / HTML + TS | △ ネイティブアドオン（C++）かFFIが必要。フックのコールバックとメッセージループを扱うのは苦しい | ✕ Chromium一式が常に載る（100MB超） | ✕ 100MB超 |
| D. C++（Win32 / Qt） | C++ | ◎ | ◎ | ◯ |
| E. Python（PySide6 / pystray） | Python | ◯ ctypes / pywin32 | △ インタープリターとQtが載る | ✕ PyInstallerは重く、ウイルス対策ソフトに誤検知されやすい |
| F. Rust + ネイティブUI（egui / Slint など） | Rust / Rust | ◯（Aと同じ） | ◎ ウィンドウを開いていても軽い | ◎ |

数値は一般的な目安であり、この環境で測ったものではない。Aの実測値は段階1で測り、下の「結果の記録」に書く。

## 決定

**A. Tauri 2 を使う。本体はRust、画面はReact + TypeScript（Vite）とする。**

### 理由

1. **常駐時のメモリが最も少ない部類に入る。** ウィンドウを閉じたときに破棄すれば、WebView2のプロセスはなくなり、Rustの本体だけが残る。B（ランタイムが常に載る）、C、Eより軽い。
2. **Win32 APIを制限なく呼べる。** `windows` クレート（Microsoft公式）で、フックや隠しデスクトップを含む全APIを呼べる。Bより冗長だが、Windows固有の処理は段階2以降のモジュールに閉じ込めるので、その冗長さは全体には広がらない。
3. **配布が軽い。** exeは数MBで、WebView2はWindows 11に標準で入っている。
4. **画面をWeb技術で柔軟に作れる。** リアルタイムのログ表示（色分け、折りたたみ、仮想スクロール）は、Web技術のほうが早く作れる。
5. **MCPサーバーを作れる。** Rustの公式SDK（rmcp）がある。監視ロジックをTauriに依存しないクレートに分けておけば、段階3のMCPサーバーのexeからも使える。
6. **移植の余地が残る。** Tauri はmacOSにも対応しているので、監視部分は移植できる。

### 他を選ばなかった理由

- **B（C#）**: Win32の書きやすさでは最も優れており、僅差の次点。ランタイムが常に載る分、常駐時のメモリで劣るため、メモリを最重視する今回は選ばなかった。「Windows専用で良く、Win32まわりを最も読み書きしやすくしたい」という優先順位なら、Bが妥当になる。
- **C（Electron）**: 全部TypeScriptで書けるが、常駐時のメモリと配布サイズが要件に合わない。Win32のフックも扱いにくい。
- **D（C++）**: 性能とWin32の扱いは最良だが、画面を作る手間が大きい。メモリ安全性も、コーディングとレビューの質に強く左右される。
- **E（Python）**: 試作には向くが、常駐ツールとして配布するには重く、誤検知の問題もある。
- **F（Rust + ネイティブUI）**: **ウィンドウを開いている間のメモリはAより少ない。** ただし、ウィンドウを開くのは状況を確かめる短い時間だけで、閉じればAとの差はほぼなくなる。一方、ログ表示のようなリッチな画面、日本語の入力や表示、部品の充実度ではWeb技術に劣る。メモリの差が効くのは開いている間だけなので、画面の作りやすさを優先してAにした。

### 画面のライブラリ（React）について

React を選んだのは、部品（仮想スクロールなど）が充実しているためと、AIがコードを書くときの精度が安定しているため。Svelte や Solid のほうがバンドルは小さいが、WebView2そのものが使うメモリに比べれば差は無視できる。この選択は深く比較していない。画面の規模が小さいので、後で変えるコストも小さい。

## 結果として受け入れること

- **ウィンドウは閉じたら破棄し、開くたびに作り直す。** 隠すだけでは WebView2 のプロセスが残り、メモリの利点がなくなる。開くたびに数百ms程度の待ちが生じる。
- Rust の Win32 呼び出しは `unsafe` が多くなる。Win32を呼ぶ処理は専用のモジュールに集め、安全なラッパーを通して使う。
- WebView2 ランタイムに依存する。Windows 11には標準で入っているが、無効にされている環境では起動時に案内を出す。
- 本体（Rust）と画面（TypeScript）の2つの言語を扱う。
